main.rs

The entry point is thin orchestration

Your main function is a solid example of idiomatic Rust application structure. It parses command-line arguments, initializes logging, creates directories, opens the database, runs migrations, builds the pipeline, scans the inbox, reconciles interrupted work, optionally starts the file watcher, and then spawns worker threads. 

fn main() -> Result<()> {
    let cli = Cli::parse_args();
    logging::init(cli.verbose);

    fs::create_dir_all(&cli.inbox)?;
    fs::create_dir_all(&cli.outbox)?;

    let db = Database::open(&cli.db)?;
    db.run_migrations("migrations")?;

    let failpoint = cli
        .failpoint
        .as_deref()
        .map(Failpoint::from_str)
        .transpose()
        .context("invalid --failpoint value")?;

    let pipeline = Pipeline::new(...);
    let discovered = pipeline.scan_and_enqueue(&cli.inbox)?;
    pipeline.reconcile_startup()?;
}
Teaching point: main.rs coordinates the system. It does not swallow all the logic. That separation makes the code easier to explain and easier to trust.

What the code does

The Cli struct uses Clap derive macros to define command-line arguments like inbox path, outbox path, database path, worker count, lock timeout, failpoint selection, and verbosity.

Enums are the backbone of crash recovery

This is where Rust really starts to pay off in a way beginners can feel. The enums in state.rs define legal states instead of leaving workflow state as random text values scattered through the code.

    Queued,
    Compressing,
    Compressed,
    Hashing,
    Hashed,
    Moving,
    Moved,
    Recording,
    Done,
}
Queued

The file has been discovered and stored, but no worker is currently processing it.

Compressing

The worker is generating a gzip temporary artifact under the outbox .tmp directory.

Hashing

The code computes or reuses a SHA-256 hash for the original source file.

Moving

The temp file is atomically renamed into its final destination.

Recording

The database is finalized so the row becomes durably complete and unlocked.

Because PipelineStep derives ordering traits, the worker can compare steps directly. That makes restart logic clearer and safer than hand-written integer stages.

Idempotency

If the final output already exists, the pipeline updates metadata and marks the job done rather than duplicating work.

Checkpointing

fs_ops.rs

Ownership and Drop show up in a very real way

TempArtifact is one of the strongest Rust teaching examples in the whole codebase. It owns the temporary output file and cleans it up automatically unless it gets committed. 

pub struct TempArtifact {
    path: PathBuf,
    committed: bool,
}

impl TempArtifact {
    pub fn commit(mut self, final_path: &Path) -> Result<(), FsOpsError> {
        if let Some(parent) = final_path.parent() {
            fs::create_dir_all(parent)?;
        }
        fs::rename(&self.path, final_path)?;
        self.committed = true;
        Ok(())
    }
}

impl Drop for TempArtifact {
    fn drop(&mut self) {
        if !self.committed {
            let _ = fs::remove_file(&self.path);
        }
    }
}
This is the Rust idea in a single example: the lifetime of the value controls the lifetime of the resource.
db.rs

The database layer makes the pipeline resumable

What the DB functions do

  • claim_next_job selects a row and assigns it to a worker.
  • checkpoint_start records that a stage has begun.
  • checkpoint_complete records that a stage has finished.
  • set_sha_if_missing preserves an existing hash through COALESCE.
  • set_output_path stores the final artifact path.
  • mark_failed records errors and releases locks.
  • mark_done_and_release finalizes the row and clears worker ownership.

Why it matters

Rust gives type safety and memory safety, but the recovery story here comes from explicit persisted state transitions. That is what lets the program survive crashes without losing track of reality.
